My job is to set that direction, build the programs that make it real, and put people and tooling behind it.

🧩 The belief driving this work: unified controls, engineered

Most compliance programs test the same control five different ways because five different frameworks happen to ask for it. I led the effort to change that — building a common controls framework that unifies testing across four compliance frameworks, so one piece of evidence satisfies multiple auditors instead of one team repeating the same work four times.

That effort is the clearest expression of how I think GRC should work going forward:

Controls should be mapped once, tested once, and reused everywhere they apply — not re-litigated framework by framework
Evidence collection should be automated wherever the audit trail allows it, freeing analysts for judgment calls instead of screenshots
AI-assisted tooling has a real role in control-gap analysis — I've used it to speed up gap analysis and cut duplicate audit effort, and I expect that role to grow
A GRC platform is infrastructure, not a filing cabinet — I led the implementation of our GRC tool and built out five modules (Controls Compliance, Policy & Procedure Maintenance, Third-Party Risk Management, Internal Audit, and Enterprise Risk Management) so the program runs on a system, not on spreadsheets

I don't write the automation myself. I set the direction, build the team and the framework it operates in, and create the conditions where GRC engineering — whoever builds it — has somewhere real to land.
